# Context

MathMind is designed to be a long-lived platform with contributions from multiple engineers and AI assistants. Without stable governance, architectural direction can drift over time, leading to inconsistent implementations, duplicated work, and conflicting design decisions.

To maintain consistency, core governance artifacts must be treated as controlled engineering assets.

---

# Problem

Allowing unrestricted modification of governance documents creates several risks:

- Architectural drift
- Conflicting implementation patterns
- Loss of decision history
- AI-generated inconsistencies
- Unpredictable development practices
- Increased maintenance costs

The project requires a mechanism to distinguish foundational decisions from ordinary documentation.

---

# Decision

The following documents are designated as **Frozen Governance Documents**:

- MM-GOV-001 — Project Handbook
- MM-GOV-002 — Decision Index
- DB-000 — Database Architecture & Standards
- Approved ADRs

Once approved, these documents become the authoritative source for engineering decisions.

No implementation may intentionally conflict with an approved governance document.

---

# Governance Rules

## Rule 1 — Governance Takes Precedence

Approved governance documents override:

- Feature documentation
- Design notes
- Inline comments
- AI-generated recommendations
- Unreviewed implementation choices

---

## Rule 2 — Changes Require Approval

Changes to frozen governance documents require:

1. A documented proposal
2. Technical review
3. Architecture review
4. Engineering approval
5. Version increment
6. Changelog entry

---

## Rule 3 — No Silent Changes

Governance documents must never be modified without:

- Documented rationale
- Version update
- Review record
- Changelog update

---

## Rule 4 — Backward Compatibility

Governance updates should preserve compatibility whenever practical.

Breaking governance changes require a new major version.

---

# AI Responsibilities

AI assistants working on MathMind shall:

1. Read the Project Handbook before generating code.
2. Review the Decision Index.
3. Follow all applicable ADRs.
4. Avoid introducing conflicting architectural patterns.
5. Recommend governance changes rather than applying them automatically.

AI-generated output must respect approved project decisions.

---

# Engineering Responsibilities

Engineers are responsible for:

- Maintaining governance accuracy
- Reviewing proposed changes
- Preventing architectural drift
- Updating related documentation when governance changes

---

# Exceptions

Temporary deviations are permitted only when:

- A critical production issue requires immediate mitigation.
- The deviation is documented.
- A follow-up ADR or governance update is created if the change becomes permanent.

---

# Compliance

Pull requests affecting governance documents must include:

- Architectural justification
- Updated version number
- Changelog entry
- Review approval

Changes that do not meet these requirements must not be merged.

---

# Benefits

This policy provides:

- Stable architectural direction
- Consistent engineering practices
- Reliable AI collaboration
- Reduced technical debt
- Clear decision authority
- Improved onboarding
- Long-term maintainability

---

# Consequences

Positive:

- Predictable project evolution
- Better traceability
- Easier reviews
- Fewer conflicting implementations

Trade-offs:

- Governance changes require additional review.
- Decision-making becomes more deliberate.

These trade-offs are acceptable because governance stability is essential for a production platform.
