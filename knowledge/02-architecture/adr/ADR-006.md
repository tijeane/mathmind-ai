# Context

MathMind relies on persistent storage for user accounts, educational content, learning progress, AI interactions, analytics, and operational data. The database architecture must provide consistency, security, scalability, and maintainability while supporting future growth.

This ADR establishes the official database strategy for the platform.

---

# Problem

Without a standardized database strategy:

- Schema design becomes inconsistent.
- Data integrity degrades over time.
- Performance becomes unpredictable.
- Security policies vary between tables.
- AI-generated migrations become unreliable.
- Database maintenance becomes increasingly expensive.

A single architectural approach is required for all database development.

---

# Decision

MathMind adopts **PostgreSQL**, managed through **Supabase**, as the canonical relational database platform.

All persistent application data shall reside within PostgreSQL unless an approved ADR authorizes an additional data store.

---

# Core Principles

Database architecture follows these principles:

- Single source of truth
- Strong relational integrity
- Security by default
- Explicit schema evolution
- Backward-compatible migrations
- Performance through proper indexing
- Auditability
- Observability

---

# Database Platform

Approved technologies:

| Component | Technology |
|-----------|------------|
| Database | PostgreSQL |
| Platform | Supabase |
| Migration Tool | SQL Migrations |
| Connection | Secure TLS |
| Authentication | Supabase Auth |

No alternative database platform may be introduced without an approved ADR.

---

# Data Organization

The database should be organized into logical domains.

Examples include:

- Identity
- Courses
- Lessons
- Exercises
- Assessments
- Learning Progress
- AI Conversations
- Analytics
- Administration
- System Configuration

Each domain should remain logically independent while maintaining referential integrity.

---

# Primary Keys

All tables shall use:

- UUID primary keys

Advantages include:

- Distributed compatibility
- Better security than sequential IDs
- Easier data synchronization
- Stable API references

---

# Relationships

Database relationships must use explicit foreign keys.

Rules:

- Foreign key constraints required
- Cascading deletes only when appropriate
- Junction tables for many-to-many relationships
- Avoid duplicate relationship data

Referential integrity is mandatory.

---

# Naming Standards

Tables

- snake_case
- descriptive names

Columns

- snake_case
- foreign keys end with `_id`

Indexes

- descriptive names

Constraints

- consistently prefixed

Views

- descriptive names

Functions

- verb-oriented names

Consistency is preferred over brevity.

---

# Migration Strategy

Every schema modification shall use a migration.

Migration requirements:

1. Immutable after execution
2. Sequential ordering
3. Version controlled
4. Reviewed before merge
5. Tested in staging
6. Rollback strategy documented

Direct production schema edits are prohibited.

---

# Row-Level Security

Row-Level Security (RLS) is enabled by default.

Policies should enforce:

- User isolation
- Role-based access
- Least privilege
- Secure service access

No table containing user data should be publicly accessible without an approved exception.

---

# Indexing Strategy

Indexes should exist for:

- Primary keys
- Foreign keys
- Frequently filtered columns
- Frequently joined columns
- Unique business identifiers

Indexes should be reviewed periodically using production query metrics.

---

# Transactions

Multi-step write operations shall execute within database transactions whenever atomicity is required.

Transactions should:

- Prevent partial writes
- Preserve consistency
- Handle rollback correctly

---

# Soft Deletes

Where business requirements require historical records:

Preferred approach:

```text
deleted_at TIMESTAMP NULL
```

Soft deletes should be used selectively rather than universally.

---

# Auditing

Critical entities should record:

- created_at
- updated_at
- created_by
- updated_by

Where appropriate:

- deleted_at
- deleted_by

Audit history improves traceability and compliance.

---

# Performance Strategy

Database optimization priorities:

1. Correct schema design
2. Proper indexing
3. Efficient queries
4. Pagination
5. Query monitoring
6. Controlled denormalization

Premature optimization should be avoided.

---

# Backup & Recovery

Operational standards:

- Automated backups
- Point-in-time recovery
- Periodic restore testing
- Disaster recovery documentation
- Recovery verification

Recovery procedures should be validated regularly.

---

# Security

Security requirements include:

- Encrypted connections
- Least privilege
- Secret management outside source control
- Parameterized queries
- Input validation
- Audit logging

Application code must never rely solely on client-side validation.

---

# AI Responsibilities

AI assistants shall:

1. Generate normalized schemas.
2. Respect naming conventions.
3. Create migrations rather than editing schemas directly.
4. Preserve backward compatibility.
5. Avoid destructive migrations unless explicitly approved.
6. Follow RLS and security standards.

AI-generated SQL should always be reviewed before deployment.

---

# Benefits

This strategy provides:

- Reliable data integrity
- Consistent schema evolution
- Better scalability
- Improved security
- Easier maintenance
- Predictable migrations
- Better AI-generated database code

---

# Consequences

Positive:

- Stable database architecture
- Easier troubleshooting
- Better operational reliability
- Lower maintenance costs

Trade-offs:

- Migration discipline is required.
- Database reviews become mandatory.

These trade-offs are acceptable because they significantly reduce long-term operational risk.

---

# Compliance

Database work is complete only when:

- Migration exists
- Schema reviewed
- RLS policies implemented
- Tests updated
- Documentation updated
- Performance reviewed
- Security validated
