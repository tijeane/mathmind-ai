# Context

MathMind is designed as a modern, cloud-native AI learning platform. To maximize long-term maintainability, contributor productivity, and deployment reliability, the project requires a standardized technology stack.

Allowing contributors to introduce technologies on an ad hoc basis would increase maintenance costs, fragment the codebase, and complicate onboarding.

This ADR defines the official technology stack for MathMind.

---

# Problem

Without an approved technology baseline:

- Multiple frameworks may be introduced.
- Similar functionality could be implemented using different libraries.
- AI assistants may generate inconsistent code.
- Developer onboarding becomes more difficult.
- Long-term maintenance costs increase.

The project requires a single, stable technology stack.

---

# Decision

MathMind adopts the following technology stack as the official engineering baseline.

Any significant deviation requires a new ADR.

---

| Technology | Purpose |

| TypeScript | Primary programming language |

| React Hook Form | Forms |
| Zod | Validation |

# Backend

| Technology | Purpose |
|------------|---------|
| Next.js Route Handlers | API layer |
| TypeScript | Backend language |
| Node.js (LTS) | Runtime |
| Server Actions | Server-side operations where appropriate |

---

# Database

| Technology | Purpose |
|------------|---------|
| PostgreSQL | Primary relational database |
| Supabase | Managed database platform |
| SQL Migrations | Schema management |

Database standards are governed by **DB-000**.

---

# Authentication

Authentication is centralized.

Approved technologies:

- Supabase Authentication
- JWT sessions
- OAuth providers (future)
- Email/password authentication

Role-based authorization will be implemented within the application layer.

---

# AI Platform

Primary AI provider:

- OpenAI

Future provider support may include:

- Anthropic
- Google Gemini
- Local LLMs

The AI abstraction layer should isolate provider-specific implementation details.

---

# API Standards

APIs shall follow REST principles unless an approved ADR introduces an alternative architecture.

API requirements:

- JSON payloads
- Versioning
- Validation
- Authentication
- Rate limiting
- Consistent error responses

---

# Testing

Approved testing stack:

| Layer | Technology |
|--------|------------|
| Unit | Vitest |
| Component | React Testing Library |
| End-to-End | Playwright |

All new features should include automated tests appropriate to their scope.

---

# Development Tools

Approved tools:

- Git
- GitHub
- Cursor
- VS Code
- ChatGPT
- Claude
- GitHub Actions

Additional tooling may be adopted through the ADR process.

---

# Deployment

Production deployment targets:

- Vercel (application)
- Supabase (database)
- GitHub Actions (CI/CD)

Future infrastructure changes require architectural review.

---

# Package Management

Standard tooling:

- npm

All dependencies should be:

- Actively maintained
- Well documented
- Widely adopted
- Compatible with the approved stack

Unused dependencies should be removed regularly.

---

# Dependency Policy

Before adding a dependency, contributors should verify:

- Active maintenance
- Community adoption
- Security history
- License compatibility
- Bundle size impact
- Existing alternatives

Prefer built-in platform capabilities before introducing third-party libraries.

---

# Coding Standards

Engineering standards include:

- TypeScript strict mode
- ESLint
- Prettier
- Consistent naming conventions
- Modular architecture
- Small reusable components

These standards apply across the entire repository.

---

# AI Responsibilities

AI assistants shall:

1. Use only approved technologies.
2. Avoid introducing new frameworks.
3. Follow established coding standards.
4. Generate TypeScript by default.
5. Reuse existing libraries before suggesting new ones.

If a requested solution requires a new technology, the AI should recommend creating a new ADR rather than introducing it directly.

---

# Benefits

The approved technology stack provides:

- Consistent architecture
- Faster onboarding
- Better AI-generated code
- Lower maintenance costs
- Predictable deployments
- Improved reliability
- Easier upgrades

---

# Consequences

Positive:

- Stable engineering platform
- Consistent implementation patterns
- Reduced technical debt
- Simplified documentation

Trade-offs:

- New technologies require formal review.
- Contributors must work within the approved stack.

These trade-offs are acceptable because they preserve long-term maintainability.

---

# Compliance

A feature is considered compliant when:

- It uses approved technologies.
- It follows project coding standards.
- It does not introduce unauthorized dependencies.
- It passes automated testing.
- Documentation is updated when necessary.
