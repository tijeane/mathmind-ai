# ADR-003 — Branching & Release Strategy

| Field           | Value                      |
| --------------- | -------------------------- |
| Status          | Approved                   |
| Version         | 1.0.0                      |
| Date            | 2026-08-07                 |
| Decision Makers | MathMind Architecture Team |

---

# Context

MathMind requires a consistent Git workflow that supports rapid development while maintaining production stability and high code quality.

The workflow must be simple enough for individual contributors while scaling to a larger engineering team.

---

# Decision

The repository will use **GitHub Flow**.

The default branch is:

* `main`

`main` must always remain deployable.

Development occurs on short-lived branches.

---

# Branch Naming

Feature work:

```
feature/<short-description>
```

Bug fixes:

```
fix/<short-description>
```

Documentation:

```
docs/<short-description>
```

Maintenance:

```
chore/<short-description>
```

Refactoring:

```
refactor/<short-description>
```

Performance:

```
perf/<short-description>
```

Tests:

```
test/<short-description>
```

Releases:

```
release/<version>
```

Hotfixes:

```
hotfix/<version>
```

Examples:

```
feature/auth
feature/student-dashboard
fix/session-timeout
docs/project-handbook
```

---

# Commit Convention

All commits shall follow Conventional Commits.

Examples:

```
feat(auth): implement login
fix(api): handle invalid token
docs: update handbook
refactor(db): simplify queries
test(auth): add login tests
```

---

# Pull Requests

Every pull request must:

* target `main`
* pass CI
* resolve merge conflicts
* include a clear description
* reference the implementation task or issue
* update documentation when required

---

# Review Policy

Before merge:

* at least one review is required
* all requested changes must be addressed
* CI must succeed
* no unresolved review comments
* no failing tests

---

# Merge Strategy

Use **Squash and Merge** for feature branches.

Benefits:

* clean history
* easier reverts
* meaningful commit log
* reduced merge noise

Direct commits to `main` are discouraged except for repository initialization or explicitly approved administrative changes.

---

# Releases

Versioning follows Semantic Versioning.

```
MAJOR.MINOR.PATCH
```

Examples:

```
1.0.0
1.1.0
1.1.1
2.0.0
```

Release tags:

```
v1.0.0
v1.1.0
```

---

# Hotfix Process

Critical production issues use:

```
hotfix/<version>
```

Steps:

1. Branch from `main`.
2. Implement the fix.
3. Run all required tests.
4. Open an expedited pull request.
5. Merge after approval.
6. Tag the release.
7. Deploy.

---

# Branch Protection

The `main` branch should enforce:

* pull requests required
* passing status checks
* up-to-date branch before merge
* signed commits (recommended)
* force pushes disabled
* branch deletion disabled

---

# Compliance

All contributors shall follow this workflow.

Any deviation requires approval through a new Architecture Decision Record.
