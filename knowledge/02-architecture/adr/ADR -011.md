# ADR-011
# Documentation First Development

---

# Context

Several existing governance documents already assume a "Documentation First Development" policy exists — MM-ARC-001 lists it as an architectural principle, and MM-GOV-001 (Project Handbook) requires every session to begin by reading governance before writing code. `DECISION_INDEX.md` originally listed this concept under ADR-001, but ADR-001 was instead written to record a Technology Stack decision (now superseded by ADR-005). The Documentation First concept itself was never actually drafted under any ADR number.

This ADR formally establishes the policy those other documents already assume, closing that gap under a new, non-conflicting number.

---

# Problem

Without an explicit, approved Documentation First policy:

- The Handbook's "Session Startup" and "Knowledge Hierarchy" sections rest on an undefined foundation.
- Contributors and AI assistants have no single authoritative statement of *when* documentation must precede implementation versus when it may follow.
- Architectural intent can diverge from what is written down, since nothing requires the two to be created in a specific order.
- Cross-references to this concept elsewhere in the knowledge base (MM-ARC-001, and ADR-005's own Related Documents list) point to a number that no longer holds this content.

---

# Decision

MathMind adopts **Documentation First Development**: architecturally significant decisions are documented — at minimum as an ADR stub with Context, Problem, and proposed Decision — *before* the corresponding implementation is written, not only afterward as a record.

Documentation is treated as a deliverable of equal standing to code, not an artifact produced after the fact to describe what was already built.

---

# Rule 1 — What Requires Documentation Before Code

The following require a documented decision (ADR, or an update to an existing architecture/product document) before implementation begins:

- New subsystems or services
- New database domains or schema patterns not covered by DB-000 / MM-DB-001A
- New external integrations or AI providers
- Changes to authentication, authorization, or data classification
- Any deviation from an approved ADR

Routine feature work that fits entirely within already-approved architecture (e.g., a new lesson type using existing APIs and schema patterns) does not require a new ADR, but should still update the relevant `knowledge/` document as part of the same change, per ADR-010's documentation-with-code requirement.

---

# Rule 2 — Session Startup

Every engineering or AI session begins by following MM-GOV-001's Session Startup sequence: read the Handbook, review the Decision Index, review applicable ADRs, and confirm frozen architecture before writing code. This ADR is the architectural basis for that requirement.

---

# Rule 3 — Documentation Debt Is Tracked, Not Silent

Where documentation cannot be completed before an urgent implementation (e.g., a production hotfix), the gap must be explicitly logged and resolved in a follow-up, not left indefinitely. An empty or stub governance file is treated as open documentation debt, not as an implicit "no policy" — as happened with this very ADR slot originally being assumed to exist under ADR-001.

---

# AI Responsibilities

AI assistants shall:

1. Check whether a request touches an area requiring documentation-first treatment (Rule 1) before generating implementation code.
2. If it does, and no corresponding document or ADR exists, draft one and present it for approval before proceeding with implementation — rather than writing code first and documenting afterward.
3. Never present a stub, empty, or mismatched governance document as if it were approved and authoritative.
4. When filling a previously empty governance slot, verify the intended topic against the Decision Index and all documents that cross-reference it, rather than assuming the slot is free to redefine.

---

# Consequences

Positive:

- Architecture and documentation stay synchronized by construction rather than by discipline alone.
- Closes the gap between documents that assumed this policy existed and the policy itself.

Trade-offs:

- Some upfront documentation work is required before implementation can start on architecturally significant features.

This trade-off is accepted, as it is the same trade-off already assumed by MM-GOV-001 and MM-ARC-001; this ADR makes it explicit and approvable.
