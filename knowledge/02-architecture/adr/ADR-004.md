# Context

MathMind is intended to be a long-lived software platform developed by multiple engineers and AI assistants. As the codebase grows, a consistent repository structure is essential for maintainability, discoverability, onboarding, and automation.

An unstructured repository increases cognitive load, duplicates functionality, and makes AI-generated contributions less reliable.

This ADR establishes the canonical repository organization.

---

# Problem

Without a defined repository structure:

- Similar functionality is implemented in multiple locations.
- Documentation becomes difficult to locate.
- Module ownership becomes unclear.
- AI assistants generate inconsistent file locations.
- Refactoring becomes increasingly expensive.

The project requires a single, authoritative repository layout.

---

# Decision

MathMind adopts a **feature-oriented repository structure** with clearly separated concerns.

The repository shall organize:

- Governance
- Product documentation
- Architecture
- Database
- APIs
- AI assets
- Application code
- Infrastructure
- Testing
- Automation

Each top-level directory has a well-defined purpose.

---

---

# Knowledge Directory

The `knowledge/` directory is the project's documentation source of truth.

Its responsibilities include:

- Governance
- Product strategy
- Architecture
- Database documentation
- AI guidance
- API specifications
- Implementation planning
- Research

Documentation should remain version-controlled alongside the codebase.

---

# Architecture Directory

The architecture section contains:

- System architecture
- Architecture diagrams
- ADRs
- Design standards

All approved ADRs reside in:

```text
knowledge/02-architecture/adr/
```

No duplicate ADR directories should exist elsewhere in the repository.

---

# Database Directory

Database documentation contains:

- Schema standards
- Entity documentation
- Migration strategy
- Database ADR references
- Performance guidance

Operational migration scripts belong in the application-level `database/` directory, while documentation belongs under `knowledge/03-database/`.

---

# Application Code

Application source code should be organized by responsibility rather than technology alone.

Examples:

- `app/` – application routes and pages
- `components/` – reusable UI components
- `lib/` – shared utilities
- `services/` – business logic
- `database/` – migrations and database assets
- `tests/` – automated testing

Business logic should not be duplicated across layers.

---

# Documentation Rules

Every major subsystem should include corresponding documentation.

Examples:

- API → API documentation
- Database → Database documentation
- Authentication → Architecture documentation
- AI → AI documentation

Implementation and documentation must evolve together.

---

# Naming Conventions

Repository naming standards:

- lowercase
- kebab-case for directories where appropriate
- snake_case for database objects
- PascalCase for React components
- descriptive filenames
- avoid abbreviations unless widely recognized

Consistency is preferred over personal preference.

---

# Ownership

| Area | Primary Owner |
|------|---------------|
| Governance | Engineering |
| Architecture | Chief Architect |
| Product | Product Owner |
| Database | Engineering |
| APIs | Engineering |
| AI | Engineering |
| Implementation | Engineering Team |

Ownership defines review responsibility rather than exclusive editing rights.

---

# AI Responsibilities

AI assistants shall:

1. Place files in the correct directory.
2. Reuse existing modules before creating new ones.
3. Follow naming conventions.
4. Avoid duplicate implementations.
5. Update documentation when introducing new modules.

When uncertain, AI should preserve the existing repository structure rather than invent a new one.

---

# Repository Evolution

The repository structure is expected to evolve over time.

However:

- Top-level directory changes require an approved ADR.
- Major reorganizations require migration documentation.
- Existing references must be updated to avoid broken links.

Repository changes should minimize disruption to contributors.

---

# Benefits

This repository organization provides:

- Faster onboarding
- Improved discoverability
- Consistent AI-generated output
- Reduced duplication
- Clear ownership
- Easier maintenance
- Better documentation alignment
- Predictable project structure

---

# Consequences

Positive:

- Uniform project organization
- Easier navigation
- Simplified automation
- Better scalability

Trade-offs:

- Contributors must follow established conventions.
- Structural changes require formal review.

These trade-offs are acceptable because repository consistency improves long-term maintainability.

---

# Compliance

A pull request affecting repository organization is complete only when:

- Files follow approved locations.
- Naming conventions are respected.
- Documentation is updated.
- No duplicate structures are introduced.
- Existing references remain valid.
