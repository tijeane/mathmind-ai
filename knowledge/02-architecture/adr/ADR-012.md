# ADR-Based Architecture Changes

# Context

`DECISION_INDEX.md` already describes a "Decision Review Process" (Identify need → Draft ADR → Technical review → Architecture approval → Update Decision Index → Implement → Verify compliance) and `PROJECT_HANDBOOK.md` describes an "ADR Process" (required fields: Context, Problem, Options, Decision, Consequences, Status, Date; sequential numbering; never delete). Both assume a formal ADR governing *how ADRs themselves are created, reviewed, and superseded* exists at ADR-003. It does not — ADR-003 was instead written to record a Branching & Release Strategy decision.

This ADR formalizes the ADR process itself under a new, non-conflicting number, consolidating what the Handbook and Decision Index already describe into one authoritative reference.

---

# Problem

Without a single authoritative ADR governing the ADR process:

- The rules for when an ADR is *required* versus optional are scattered and informal.
- There is no explicit definition of what counts as an "architecturally significant" change requiring an ADR.
- The Handbook and Decision Index each describe part of the process, but neither is itself an ADR, so the process has no formal Approved/Proposed lifecycle of its own.
- As demonstrated by ADR-001 and ADR-003 being filled with content unrelated to their originally catalogued titles, there was no enforced check that new ADR content matches its intended topic before being marked Approved.

---

# Decision

MathMind formalizes **ADR-Based Architecture Changes**: any change to architecture, technology stack, database strategy, security model, API design, or other frozen governance content must go through a documented ADR, following the lifecycle and template defined below.

---

# Rule 1 — When an ADR Is Required

An ADR is required for changes to:

- System or service architecture
- Technology stack or core platform choices
- Database strategy or schema patterns (beyond routine additions covered by DB-000)
- Security model, authentication, or authorization
- API design conventions
- Any other document in `00-governance/` or `02-architecture/`

Routine feature implementation within already-approved architecture does not require a new ADR (see ADR-011, Rule 1).

---

# Rule 2 — ADR Lifecycle

ADRs move through the following statuses, matching `DECISION_INDEX.md`:

Proposed → In Review → Approved → Implemented → Superseded / Rejected

- **Proposed**: drafted, not yet reviewed.
- **In Review**: under technical/architecture review.
- **Approved**: official project direction; the Decision Index must be updated in the same change.
- **Implemented**: reflected in production code.
- **Superseded**: replaced by a newer ADR; the original is retained unmodified with a Supersession Notice added, never deleted or overwritten.
- **Rejected**: considered and not adopted; retained for historical record.

---

# Rule 3 — Template Requirements

Every ADR must include, at minimum: Context, Problem, Decision, Consequences, Status, Version, Date, and Owner. This matches the template already in use across ADR-002 through ADR-010.

---

# Rule 4 — Numbering & Immutability

- ADRs are numbered sequentially and never renumbered or deleted.
- Before drafting a new ADR, the author must check `DECISION_INDEX.md` for the next available number **and** confirm no existing document already cross-references that number under a different intended topic (the failure mode that produced the ADR-001/ADR-003 mismatch this ADR is partly a response to).
- If a slot's intended topic and its actual content diverge, the correct fix is to (a) update the Decision Index to reflect the real content, and (b) draft the originally-intended concept under a new number — not to silently overwrite the existing file.

---

# Rule 5 — Superseding Process

To supersede an ADR:

1. Draft the new ADR with a Related Documents reference to the ADR it replaces.
2. Add a Supersession Notice to the old ADR's status field and a short note — do not remove or rewrite its historical content.
3. Update `DECISION_INDEX.md` in the same change to reflect the new status of both ADRs.

---

# AI Responsibilities

AI assistants shall:

1. Check `DECISION_INDEX.md` and all cross-references before drafting or filling any ADR slot.
2. Never mark an ADR Approved on their own authority — draft as Proposed and route for Engineering/Architect approval.
3. When correcting a mismatch between an ADR's catalogued title and its actual content, follow Rule 4 rather than overwriting existing approved content.

---

# Consequences

Positive:

- Consolidates process rules already implied by the Handbook and Decision Index into one authoritative, versioned document.
- Adds an explicit safeguard (Rule 4) against the exact drift that left ADR-001 and ADR-003 mismatched with the Decision Index for an extended period.

Trade-offs:

- Adds a checklist step (checking cross-references) before drafting new ADRs.

This trade-off is accepted as a small cost relative to the governance-integrity risk it prevents.
