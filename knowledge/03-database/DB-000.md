# Purpose

This document defines the database architecture, standards, conventions, governance, and operational policies for the MathMind platform.

It serves as the authoritative reference for database design, schema evolution, migrations, security, performance, compliance, and long-term maintainability.

---

# Objectives

The database architecture is designed to:

- Maintain a single source of truth
- Ensure data integrity
- Support scalable cloud-native deployment
- Protect student information
- Enable AI-powered learning
- Support analytics and reporting
- Provide reliable disaster recovery
- Remain maintainable over many years

---

# Database Principles

The platform follows these principles:

- Normalize by default
- Denormalize only when justified
- Prefer explicit relationships
- Enforce integrity through constraints
- Keep business logic in application services
- Design migrations to be backward compatible
- Optimize only after measurement

# UUID Standard

Every primary key shall use:

```sql
gen_random_uuid()
```

UUID values are immutable.

Primary keys are never updated after creation.

Student information is classified into four tiers.

| Tier | Description | Examples |
|-------|-------------|----------|
| Tier 0 | Public educational content | Courses, lessons, curriculum |
| Tier 1 | Metadata | IDs, timestamps |
| Tier 2 | Personally Identifiable Information | Email, name, DOB |
| Tier 3 | Education Records | Attempts, mastery, AI conversations |

Rules:

- Tier 2 requires RLS.
- Tier 3 requires RLS.
- Tier 3 requires audit logging.
- Tier 3 follows retention policies.

# Security Helper Functions

Membership checks live inside a dedicated schema.

```
security.is_org_member()

security.is_org_admin()

security.is_guardian()

security.has_permission()
```

Never duplicate authorization logic inside policies.

---

# Row-Level Security

Never join directly against another RLS-protected table inside a policy.

Instead use SECURITY DEFINER helper functions.

Example:

```sql
create policy "members"
on courses
using (
    security.is_org_member(org_id)
);
```

Helper functions:

- SECURITY DEFINER
- STABLE
- centrally maintained

This avoids recursive RLS evaluation.

---

# Soft Deletes

Soft deletes use:

```
deleted_at
```

Application code queries database views instead of base tables.

Example:

```
vw_users_active

vw_courses_active

vw_lessons_active
```

Views automatically filter:

```sql
deleted_at IS NULL
```

Only administrative tooling accesses base tables directly.

# Foreign Key Policy

Default:

```
ON DELETE RESTRICT
```

Allowed exceptions:

```
ON DELETE CASCADE

(Junction tables only)
```

```
ON DELETE SET NULL

(Optional ownership)
```

Every exception must be documented.

# Indexing Standards

Indexes are required for:

- Primary keys
- Foreign keys
- Frequently filtered columns
- Join columns
- Business identifiers
- Lookup tables

Indexes should be reviewed periodically using production metrics.

---

# JSONB Policy

JSONB is permitted only for schema-variable data.

Examples:

```
ai_sessions.context

problems.variant_data
```

JSONB is prohibited for:

- foreign keys
- memberships
- permissions
- frequently queried fields

Every JSONB column requires:

- documented structure
- TypeScript interface
- validation before persistence

JSONB is not exempt from data classification rules.

---

# Migration Policy

Rules:

1. Every schema change uses a migration.
2. Migrations are immutable.
3. Rollback documented.
4. Tested in staging.
5. Reviewed before production.

No manual production schema edits.

# Appendix A — Approved PostgreSQL Data Types

The following data types are approved for use within the MathMind platform.

| Type | Usage | Notes |
|------|------|------|
| UUID | Primary & foreign keys | Generated with `gen_random_uuid()` |
| TEXT | General string storage | Preferred over VARCHAR unless length constraint is a business rule |
| CITEXT | Case-insensitive text | Email addresses, usernames |
| BOOLEAN | True/False values | Avoid integer flags |
| INTEGER | Small whole numbers | Counts, ordering |
| BIGINT | Large counters | Analytics, event counts |
| NUMERIC(p,s) | Exact decimals | Scores, percentages, financial values |
| REAL / DOUBLE PRECISION | Floating-point values | Scientific calculations only |
| JSONB | Schema-variable data | Requires documented schema |
| DATE | Calendar dates | Birth dates, due dates |
| TIMESTAMPTZ | Date/time values | UTC only |
| INTERVAL | Durations | Time spans |
| BYTEA | Binary data (rare) | Prefer object storage instead |
| UUID[] | Collections of UUIDs (rare) | Only with documented justification |

### Disallowed

Avoid unless approved:

- VARCHAR without business justification
- TIMESTAMP WITHOUT TIME ZONE
- MONEY
- SERIAL/BIGSERIAL for primary keys
- XML
- HSTORE

# Appendix C — Canonical Table Template

```sql
CREATE TABLE users (

    id UUID PRIMARY KEY
        DEFAULT gen_random_uuid(),

    email CITEXT NOT NULL,

    first_name TEXT NOT NULL,

    last_name TEXT NOT NULL,

    status TEXT NOT NULL,

    created_at TIMESTAMPTZ NOT NULL
        DEFAULT now(),

    updated_at TIMESTAMPTZ NOT NULL
        DEFAULT now(),

    deleted_at TIMESTAMPTZ,

    created_by UUID,

    updated_by UUID,

    deleted_by UUID,

    CONSTRAINT uq_users_email
        UNIQUE(email)

);

CREATE INDEX idx_users_email
ON users(email);
```

Every table should follow this structure unless an ADR documents an exception.

# Appendix K — SQL Style Guide

This guide governs how SQL is written across MathMind — migrations, seed scripts, views, and functions. It is a formatting standard, not a schema-design standard; it does not override any rule elsewhere in DB-000.

## Keyword Casing

- Keywords are **lowercase**: `select`, `from`, `where`, `create table`, `insert into`.
- Rationale: matches Supabase CLI and PostgREST-generated SQL conventions already in use, and reduces visual noise versus SHOUTING keywords.
- Identifiers (tables, columns, functions) are always `snake_case`, per the Naming Standards sections above.

```sql
-- Correct
select id, email
from users
where deleted_at is null;

-- Incorrect
SELECT id, email
FROM users
WHERE deleted_at IS NULL;
```

## Formatting

- One clause per line for any query with more than one clause (`select` / `from` / `where` / `order by` / etc.).
- Indent continuation lines two spaces under the clause they belong to.
- Trailing commas, not leading commas, in column lists.
- Closing parenthesis of a multi-line statement sits on its own line, aligned with the opening statement.

```sql
select
  u.id,
  u.email,
  c.title as course_title
from users u
join enrollments e on e.user_id = u.id
join courses c on c.id = e.course_id
where u.deleted_at is null
order by u.created_at desc;
```

## Aliasing

- Table aliases are short, lowercase, and derived from the table name (`users u`, `courses c`, `attempts a`).
- Every column reference in a multi-table query is qualified with its alias, even when unambiguous — this prevents breakage when columns are later added to another joined table.
- Aliases are declared with a space, never `AS` for tables (`users u`, not `users AS u`). Columns use `as` for clarity (`count(*) as attempt_count`).

## CTEs

- Prefer CTEs (`with ... as (...)`) over deeply nested subqueries once a query needs more than one level of subquery — nesting past one level is a readability and debugging cost.
- Name CTEs for what they contain, not generically (`active_enrollments`, not `cte1`).
- A CTE used only once should generally be inlined instead; reserve CTEs for reuse within the same query or genuine readability gain.

```sql
with active_enrollments as (
  select user_id, course_id
  from enrollments
  where deleted_at is null
)
select u.id, count(ae.course_id) as course_count
from users u
join active_enrollments ae on ae.user_id = u.id
group by u.id;
```

## Transactions

- Every migration that touches more than one statement is wrapped explicitly:

```sql
begin;

-- statements here

commit;
```

- Destructive or irreversible statements (drops, type changes, data backfills) require a preceding comment stating the rollback plan, per the Migration Policy section.
- Never rely on implicit autocommit for multi-statement migrations.

## Migration File Naming

- Format: `<timestamp>_<verb>_<object>.sql`, e.g. `20260803120000_create_ai_sessions.sql`, `20260810093000_add_index_attempts_user_id.sql`.
- Verb is one of: `create`, `add`, `alter`, `drop`, `backfill`, `rename`.
- One logical change per migration file — do not bundle an unrelated index addition into a table-creation migration.

## Comments

- Every migration file opens with a one-line comment stating its purpose and linking the relevant ADR or table spec if one exists.
- Inline comments explain *why*, not *what* — `-- required for FERPA retention purge job`, not `-- delete old rows`.
- Tier 2/Tier 3 columns are tagged inline per the Data Classification section: `-- TIER2: PII`, `-- TIER3: education-record`.

## Disallowed Patterns

- `select *` in application code or views (explicit column lists only). `select *` is acceptable only in ad-hoc/manual debugging queries, never committed.
- Implicit joins (comma-separated `from` lists relying on a `where` clause to join) — always use explicit `join ... on`.
- Unqualified column names in any query touching more than one table.
